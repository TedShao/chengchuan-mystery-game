# 文本、设计与后续实现工作流

目标：使每轮产出减少一个真实问题，而不是增加一套文档。流程以 GitHub 为唯一版本来源，当前已进入用户授权的工程重构阶段，继续用实际体验验证文本。

## 最短路径

**指出具体问题 → 核对事实和人物 → 改最少的场景 → 纸面反路线 → 陌生玩家观察 → 决定保留、重写或删除 → 另行进入实现。**

| 阶段 | 做什么 | 最小产物 | 不能越过的边界 |
|---|---|---|---|
| 定义 | 引用玩家困惑或可定位文本，不泛称“体验不好” | PLAN 一张任务卡 | 同时只处理一个主要体验问题 |
| 写故事 | 先公司与人物动机，再事件，再线索 | 修改 STORY | 不因某个按钮好做而改案件真相 |
| 写交互 | 让人物有自主行动，给玩家多个合理核实方法 | 修改 SLICE / INTERACTION 对应位置 | 不把阅读、预览或草稿当发送；不能靠提示答案推进 |
| 反证 | 走直接问、早停、拒绝、漏看、误判、改口、重复 | SLICE 的必要短记录 | 作者排演不是盲测；失败先删改，不追加事故 |
| 体验 | 只给当步页面，让陌生玩家自行行动 | 与版本对应的观察 | 未取得证据就记待证；不让主持人教正确路线 |
| 实现 | 仅在后续开发任务下编写已明确片段 | 独立代码改动及必要测试 | 仅按当前明确开发授权实现，不把已实现等同体验已证 |
| 发布 | 同版本技术验证、体验结论、存档兼容 | 可追溯 PR / 发布 | 文档推送不是新游戏上线 |

## Skill 如何使用

- `mystery-writer`：写作时分开作者事实、人物认知和玩家发现顺序；六表收在 STORY，不另生成平行故事。
- `game-narrative`：检查“发现—提出解释—行动核实—承担结果”能否成立；角色可拒绝、停手或让步，不只发任务。
- `mystery-reviewer`：反向重建关键推理，区分明确、推断、缺失。先报严重断点，再谈氛围。当前审查属于作者模型检查，不伪称独立评审。
- 进入开发时才按任务选择网页游戏、对话、存档或 UI 技能；不因安装了技能就把全部方法变成必填表。没有可验证问题时不建立新实验合同。

## 创作的六个硬检查

1. 谁需要这件事发生？为什么现在做，为什么不用更简单的办法？
2. 玩家用正常权限能接触谁、看到什么？资料为何本来就存在？
3. 一条事实有哪些合理解释？下一行动能区分哪两种，不能证明什么？
4. 直接问、先拒绝或提前停止后，人物会怎样合理应对？允许问题真正解决，不为续戏恢复伤害。
5. 谁实际收到哪段信息？改口改变未来，不改写过去；不同收件范围应有不同反应。
6. 删一页、一人或一轮对话是否仍成立？若成立就删。新增内容需带来独有判断、关系变化或行动后果。

## 不确定时问什么

在改变主营业务、犯罪真相、主角身份、结局尺度、开发范围或费用前，先查已明确的用户选择；真的缺决定才问用户，并说明影响。普通台词、篇幅删减、修复逻辑冲突在既有授权内直接做。来源查不到就写不足或简化，不让用户替虚构事实“背书”。

本次已确认的犯罪与结局尺度写在 PROJECT；不在每轮重复索取批准。用户明确要求不要代码时，任何技能都不能据此启动开发。

## GitHub 日常步骤

1. 读 PROJECT、PLAN 和本轮涉及的设计页；检查分支、远端更新、未提交修改。保护他人工作及只读 sources。
2. 同一问题只改稳定文档，不建新版副本。事实变化同步三个设计文件；研究只保留正在使用的证据与边界。
3. 删除文本前搜索引用与程序依赖；代码、测试、依赖和部署另有范围，不随手清理。旧稿从当前树删除，历史由 Git 保存，不保留“待参考”的副本入口。
4. 文档检查包括链接、编码、状态与人名事实一致性、旧稿入口和改动白名单。纯文档不为了好看重跑所有本地浏览器测试；现有 CI 可能仍自动运行，需如实报告。
5. 推送文档分支，更新已有 PR 的最终标题和说明；未要求合并时不因完成文字稿提前合并。需要引用当前内容时给分支链接，而非仍是旧稿的 main 链接。
6. 最后报告改了什么、删了什么、验证了什么、还缺什么。检查通过只证明相应范围，不等于好玩、合法性已核准或新游戏已发布。

工具操作见 [ONLINE-WORKFLOW](ONLINE-WORKFLOW.md)。正常路线是网页编辑、Actions 测试、main 成功后 Pages 发布；当前没有自动 PR 试玩站。保持既有免费方案，不增加付费服务。
