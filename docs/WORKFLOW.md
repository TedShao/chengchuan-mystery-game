# 重构与迭代工作流

目的：用更少的无效产出，回答“这段是否值得做、实际能否成立”。GitHub 是版本与评审场所；流程不是增加报告的理由。

## 最短工作链

**问题证据 → 决定保留还是删掉 → 冲突与调查设计 → 最小验证 → 实现一段 → 行为回归与真人体验 → 发布或退回。**

一个迭代只验证一个主要问题，同时在做的体验任务不超过一个。修复导致无法试玩的错误可以优先插入；新人物、新软件、新章节不插队。

| 阶段 | 输入 | 最小交付 | 通过条件 | 不通过怎么办 |
|---|---|---|---|---|
| G0 定义问题 | 玩家原话、具体界面或剧本段落 | PLAN 中一张任务卡 | 能说清问题、对象和本轮不做什么 | 不开工泛化的“全面优化” |
| G1 故事成立 | 现实边界、人物目标、竞争解释 | 一页冲突骨架 + 真相/认知/线索简表 | 冲突来自相互不兼容的真实需要；有可行动检验的疑问；删除可疑线索后人物仍会行动 | 重写或放弃事件，不先润色对白 |
| G2 玩家能表达判断 | G1 骨架 | 低成本分镜 / 纸面扮演，含操作对象与后果 | 至少两种合理路线；误判能反馈并继续；没有暗号输入；主角选择实际改变事件 | 改动作和反馈；必要时退 G1 |
| G3 值得生产实现 | 代理走查 + 新玩家证据 | 一份短记录及采用/修改/放弃结论 | 玩家能解释自己的猜测与验证理由，并出现自发的下一问题；没有关键无障碍/操作卡点 | 证据不足就写未定；明确无趣则放弃，不以通过率顶替 |
| G4 实现与技术验收 | 已通过的片段规范 | 代码 PR + 对应测试 | 收件边界、事件顺序、存档、重复操作和静态发布通过；变更对应规范条目 | 修实现，不临时改真相迁就代码 |
| G5 发布与回看 | 技术结果、体验结论、已知限制 | 一段发布说明 | 证据对应同一版本；旧进度保留策略明确 | 留在分支，不用线上版本当未标注实验 |

G1—G3 可以只靠文档和有人扮演角色完成。确需交互原型时，在获得相应开发任务后做可丢弃的最小片段；“没通过前不做生产重构”不等于禁止低成本实验。当前任务仅整理文档与计划。

## 每项工作只用这一张任务卡

直接写在 PLAN 中；没有协作需要时不再复制到 Issue、表格和另一个待办文档。

```text
编号 / 状态 / 当前执行角色：
问题证据：玩家原话或可定位的现象；已知与推断分开。
这轮要决定：一句话；也允许结论为删除或放弃。
改动边界：做什么、明确不做什么。
依赖：前置任务与实际证据。
验收：可观察的通过条件和否决条件。
结果：采用 / 修改 / 放弃 / 证据不足；链接到同一版本。
```

状态只用：待开始、进行中、待证据、已完成、放弃。实现完成但缺盲测，不能标整项完成。

## 戏剧冲突审查

不以“反转次数”“可疑文件数量”打分。逐项问：

1. **人物要的是否具体？** “挣钱、掩盖罪行、追回损失”还太抽象；这一场各人今天要对方做什么？
2. **合理诉求是否真的冲突？** 如果“找本人核实”不损害任何利益、大家也都接受，那是解决流程问题，尚非戏剧选择。
3. **主角为什么不能轻松置身事外？** 必须来自已展示的关系或承诺；退出仍有合法合理出口，不能靠作者强制绑架。
4. **对抗者能否采取主动？** 要有本地合理动机、可兑现的反制与让步，不能只等玩家问完所有问题。
5. **反转是否改变目标或关系？** 不只是多读一封信；先前正确的行动可能暴露另一层责任，但不能篡改已发生事实。
6. **是否存在竞争解释？** 玩家能用正常权限的行动比较；一条日志立即揭晓后，下一问题必须更有分量。
7. **删减后是否更好？** 删除一个人物、一页文件、一轮审批，若不损失独有线索、关系转折或选择后果，就删。

每项给一个具体例子和一个反例即可。六表用于保证因果，不要求每轮另写一篇完整六表报告。

## 证据与真人测试

- 玩家原话、实际运行观察、自动测试、作者推断分别标注。
- 代理知道底稿，其“关闭指引走查”能找矛盾，不能充当陌生玩家盲测。
- 新玩家先自由玩，再问“你认为发生了什么、想确认什么、为什么”。不要先讲谜底或让他评价一段作者解释。
- 每份记录必须含版本、测试范围、操作顺序、卡点、相反意见和结论。测试存档注入须明示。
- 小样本用于发现阻碍，不计算虚假的留存提升。测试规模与停止条件由当前风险和可获得的人决定；无法找到新玩家就记录待证据。
- 假设与反证保存在 [H001](experiments/H001/game-design-hypothesis.json)，是否开展实验以 PLAN 为准。结构已被否决时先重选核心事件，不能继续把旧合同当作就绪的测试方案；也不能将多项改动归因于单一机制。

## GitHub 与发布

1. 开工读 PROJECT 和 PLAN；确认远端、分支、未提交工作与相关规范。分支按问题命名，不按随手添加的版本号命名。
2. 修改旧事实前，先更新故事真相与认知；再改片段、界面和测试。台词不能反过来偷偷创造新的事实。
3. PR 描述只写问题、最终变化、删掉什么、验证、限制。不要保留废弃方案的长过程作为当前说明。
4. 普通更新用分支 / PR；用户已授权的任务不为常规可逆操作反复请求批准。故事门槛依据证据判断，不机械要求用户批准每页。
5. `main` 通过现有 Actions 后发布 Pages；**当前没有自动 PR 试玩网址**。浏览器编辑器只编辑，不执行项目。分支实验可用现有 5174 本地环境；不要为了预览提前合并，也不擅自引入收费服务。
6. 纯文档本地只检查链接、状态、格式和规范一致性；现有 CI 仍会跑游戏测试，不能声称已配置文档跳过规则。代码变更按[测试说明](../sites/chengchuan-rebuild/tests/README.md)执行。
7. 合并后更新 PLAN 的结果与 PROJECT 的基线；发布失败保留旧站。未来回滚应通过可追溯提交，先说明存档兼容，不清空用户进度。

## 文档生命周期

只有四种用途：**规范、计划、证据、参考**。提案只是候选，历史不具有规范优先级。

- 规范中只写已经决定或明确标为未定的内容；规范的批准依据记在 PLAN 的验收结果中。
- 研究引用只摘必要结论，并保留来源与日期。引用历史调研不代表本次重新核实价格、政策或案件进展。
- 对外观、剧情和行为的每轮修订，在稳定文件上改；旧版本由 Git 保存。
- 被替代或否决的长稿从当前树删除，在 DOCUMENTS 中保留固定提交链接、退役原因和恢复方法。
- 已发布行为的可信测试记录保留为证据，不让它重新成为新剧情的要求。
- 每轮结束问一次“有没有新增重复依据、旧入口或死文件”。删除清单必须有作用与依赖检查；代码删除另经回归，不能与文档整理混做。
